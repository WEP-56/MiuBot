# 产品定位与目标

**文档状态**：草案 · v0.1

## 定位

Miubot 是 **QQ 优先、可扩展到其他聊天平台的社交 Agent 工作台**。底层选择 Fork Pi，继承 Agent Core、Provider Core 和可复用的扩展设施，并围绕社交消息重构 Tool、上下文管理和 Plugin Core 的增量能力。

## 要解决的问题

1. Bot 项目功能可能很多，但接入、模型、人设、上下文配置割裂，使用门槛高。
2. Bot 不回复、回复错模型、调用工具失败时缺少清晰的解释与调试手段。
3. 群聊是多人、异步、混合模态的连续消息流，不能完全按单用户 CLI 会话建模。
4. Agent 应有自主判断空间，宿主重点保证权限、资源、运行可靠性，而非用冗长 Prompt 强制工作流。

## 核心用户

- **自托管用户**：希望配置一次平台和模型就能运行，日常通过 Web 面板维护。
- **深度玩家**：希望为不同群/个人配置人格、模型、能力、主动行为和预算。
- **插件开发者**：希望通过清晰扩展 API 接入事件、工具、适配器和页面。

## 体验主张

- **五分钟能看懂怎么配置**：引导式连接、显式测试、渐进展示高级选项（不承诺实际接入时长）。
- **操作即反馈**：配置成功不等于服务可用；连接/模型/发送分别可测。
- **配置可解释**：每项有效值都能看见来源以及是否由会话覆盖。
- **Agent 可观察**：从消息到决策、模型、工具和发送，都能通过同一 Trace 检索。
- **扩展不劫持体验**：插件能增量扩展但不能破坏核心导航、一致性与权限。

## 明确不做（早期）

- 不以兼容所有 QQ 协议、所有 Pi 扩展为 MVP 目标。
- 不把群内所有事件都强制交给大模型决策。
- 不默认向群友开放 Bash、任意文件读写或任意外网访问。
- 不为了分布式化而先搭复杂微服务；优先单机部署、可测试模块边界。

## 成功衡量

- 新增 Bot 实例连接成功率与失败定位耗时。
- 关键操作的路径长度：添加模型、切换人格、查看一条回复的 Trace。
- 消息接收/回复成功率、延迟分布、请求与模型调用成本。
- 用户覆盖配置比例与误用率（是否常因继承不清造成误配）。

## 核心原则

> Mechanically strong, cognitively weak：强机制、弱认知约束。

机制负责安全授权、输入标准化、会话隔离、并发、观察、预算与回退；模型负责在这些机制内生成内容与选择可用工具。不要把原本可由机制保证的事情退化成 Prompt 文本承诺。
